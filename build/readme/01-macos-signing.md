# macOS code signing & notarisation — one-time setup

Grafida is distributed as a downloadable `.dmg` (outside the Mac App Store), one
per architecture: arm64 (Apple Silicon) and amd64 (Intel). For the app to launch
on other people's Macs without Gatekeeper blocking it, the bundle must be
**signed with a Developer ID Application certificate** and the DMG must be
**notarised by Apple and stapled**.

This document is the **one-time** setup you do on your build machine. Once it's
done, the build signs/notarises automatically whenever the credentials are
present (see "How the build uses this", after section 5). Everything here
requires the **paid Apple Developer Program** membership you already have.

The current build is the native shell's, packaged by grafida/shell-packager
(from 0.4). The Boson build Grafida shipped up to 0.3 is described in this file
at the tags `0.1`–`0.3`.

---

## 1. Install the Command Line Tools

You don't need the full Xcode — the standalone **Command Line Tools** provide
`codesign`, `notarytool` and `stapler`, which is everything the build needs.
Install them with:

```bash
xcode-select --install
```

A dialog appears; click **Install** and wait for it to finish. Then confirm:

```bash
xcode-select -p          # should print /Library/Developer/CommandLineTools
xcrun notarytool --version
codesign --version
```

(If `xcode-select -p` points at an Xcode install you don't want, switch to the
Command Line Tools with `sudo xcode-select -s /Library/Developer/CommandLineTools`.)

---

## 2. Create a "Developer ID Application" certificate

This is the identity that signs the app for direct download. **Not** "Apple
Development" and **not** "Mac App Store" — those won't work for a notarised DMG.
Without Xcode you create it through the Developer portal, using a certificate
signing request (CSR) generated by **Keychain Access** (built into macOS):

1. **Generate a CSR.** Open **Keychain Access** →
   menu **Keychain Access ▸ Certificate Assistant ▸ Request a Certificate From a
   Certificate Authority…**. Enter your email, put your name in *Common Name*,
   leave *CA Email* blank, choose **Saved to disk**, and save
   `CertificateSigningRequest.certSigningRequest`.

2. **Create the certificate.** Go to
   <https://developer.apple.com/account/resources/certificates> → **+** →
   under *Software* choose **Developer ID Application** → continue → upload the
   `.certSigningRequest` from step 1 → **Continue** → **Download** the resulting
   `developerID_application.cer`.

3. **Install it.** Double-click the downloaded `.cer` to import it into your
   **login keychain**. Because you made the CSR on this Mac, the matching private
   key is already in the keychain, so the certificate becomes a usable signing
   identity.

> **Do NOT change the certificate's trust settings.** Leave "When using this
> certificate" at **Use System Defaults**. Setting a Developer ID *leaf*
> certificate to "Always Trust" marks it as a trust anchor
> (`kSecTrustSettingsResultTrustAsRoot`), which makes `codesign` try — and fail —
> to build a chain *to the leaf as if it were a root*, producing
> `unable to build chain to self-signed root … errSecInternalComponent`. The
> trust that matters lives on the Apple root/intermediate installed in the next
> step, not on your leaf. If you already set it to Always Trust, undo it: open the
> certificate in Keychain Access → expand **Trust** → set **When using this
> certificate** back to **Use System Defaults**.

Confirm it's present and note its exact name:

```bash
security find-identity -v -p codesigning
```

You'll see a line like:

```
1) A1B2C3...  "Developer ID Application: Nicholas K. Dionysopoulos (ABCDE12345)"
```

The quoted string is your **signing identity**; the 10-character code in
parentheses is your **Team ID**.

---

## 3. Install the Apple intermediate + root certificates

**Command-Line-Tools-only machines need this step; full Xcode does it for you.**
Your Developer ID certificate is only the leaf of a chain
(`Developer ID Application → Developer ID Certification Authority (G2) → Apple
Root CA`). Without the two upstream certificates in your keychain, `codesign`
fails with:

```
Warning: unable to build chain to self-signed root for signer "Developer ID Application: …"
… errSecInternalComponent
```

Download both from Apple's public PKI and import them into your login keychain:

```bash
cd /tmp
curl -fsSL -o DeveloperIDG2CA.cer https://www.apple.com/certificateauthority/DeveloperIDG2CA.cer
curl -fsSL -o AppleRootCA.cer     https://www.apple.com/appleca/AppleIncRootCertificate.cer
security import DeveloperIDG2CA.cer -k ~/Library/Keychains/login.keychain-db
security import AppleRootCA.cer     -k ~/Library/Keychains/login.keychain-db
```

Notes:

* If `security import` reports a certificate "already exists", that's fine — it's
  already present.
* No trust-setting change is needed; these are Apple's standard chain-building
  certificates, not your own identity.
* If your Developer ID certificate was issued by a different intermediate (check
  with `openssl x509 -in <your-cert>.pem -noout -issuer`), download the matching
  one from <https://www.apple.com/certificateauthority/> instead of the G2 CA.

Confirm the chain now resolves:

```bash
security find-certificate -c "Developer ID Certification Authority" >/dev/null && echo "intermediate present"
security find-certificate -c "Apple Root CA" >/dev/null && echo "root present"
```

## 4. Store a notarisation credential

Notarisation uploads the DMG to Apple, which scans it and returns a ticket.
`notarytool` needs to authenticate. The simplest method is an **app-specific
password**:

1. Sign in at <https://appleid.apple.com> → **Sign-In and Security** →
   **App-Specific Passwords** → **+** → name it e.g. "Grafida notarisation".
   Copy the generated `abcd-efgh-ijkl-mnop` password.

2. Store it once as a reusable keychain profile:

   ```bash
   xcrun notarytool store-credentials "grafida-notary" \
     --apple-id "nikosdion@gmail.com" \
     --team-id "ABCDE12345" \
     --password "abcd-efgh-ijkl-mnop"
   ```

   `grafida-notary` is the **profile name** the build refers to. Verify:

   ```bash
   xcrun notarytool history --keychain-profile "grafida-notary"
   ```

*(CI-friendly alternative: an App Store Connect API key — `notarytool
store-credentials --key AuthKey_XXXX.p8 --key-id XXXX --issuer <uuid>`. Same
profile-name idea.)*

---

## 5. Tell the build about your identity + profile

The scripts read the identity and notary profile from **environment variables**,
and the Phing targets forward them from `build/build.properties` (gitignored).

Add these to `build/build.properties` (copy `build/build.sample.properties`
first if you haven't):

```properties
macos.sign.identity=Developer ID Application: Nicholas K. Dionysopoulos (ABCDE12345)
macos.notary.profile=grafida-notary
```

Or, for a one-off `scripts/build-all.sh` or `scripts/make-macos-dmg.sh` run,
export them:

```bash
export MACOS_SIGN_IDENTITY="Developer ID Application: Nicholas K. Dionysopoulos (ABCDE12345)"
export MACOS_NOTARY_PROFILE="grafida-notary"
```

## How the build uses this

From 0.4 (grafida/grafida#92) the macOS release build is the native shell's, built by
**grafida/shell-packager** (a dev dependency pinned to an exact tag) from `shell-package.json` (its
`runtimes.macos` and `macos` sections) and `shell.json` (the app manifest). Entry points, all on a
Mac:

* `phing package-macos-arm` / `phing package-macos-x86` (both part of `phing package`). They
  forward `macos.sign.identity` → `MACOS_SIGN_IDENTITY` and `macos.notary.profile` →
  `MACOS_NOTARY_PROFILE`, so a normal `phing package` (or `composer build:package` / `release`)
  signs and notarises automatically.
* `composer build` (`scripts/build-all.sh`), which builds both architectures on a Mac and skips
  macOS elsewhere.
* `scripts/make-macos-dmg.sh [arm64|amd64]` (`composer build:macos`); no architecture builds both.
  Options after a second `--` go to shell-packager's `macos-dmg` step only (not `macos-app`), e.g.
  `composer build:macos -- arm64 -- --no-style`.

`composer build` and the script use whatever the shell's environment has; only Phing reads
`build/build.properties`. Per architecture the script runs two shell-packager commands:

```bash
php vendor/bin/shell-packager macos-app --config=shell-package.json --arch=<arm64|amd64> \
  --app-version=<v> --output=build/shell-macos/<arm64|amd64>/Grafida.app
php vendor/bin/shell-packager macos-dmg --config=shell-package.json --arch=<arm64|amd64> \
  --app-version=<v> --app=build/shell-macos/<arm64|amd64>/Grafida.app
```

Output: `build/dist/Grafida-<version>-macos-<arm64|amd64>.dmg` + `.sha256`. The bundle stays in
`build/shell-macos/<arm64|amd64>/Grafida.app`.

* **One bundle and one image per architecture.** arm64 for Apple Silicon; x86_64 for Intel Macs,
  tested only under Rosetta 2.
* **The runtimes are downloaded, never built here.** The shell (a grafida/shell release) and the
  phpmicro SFX (an immutable grafida/phpmicro `sfx-<YYYYMMDD>.<run>` release) are pinned by URL and
  SHA-256 in `shell-package.json`, verified on every use, and cached in
  `~/.cache/grafida-shell-packager` (`$XDG_CACHE_HOME`, or `SHELL_PACKAGER_CACHE`). There is no
  `build/sfx/`. Bumping a pin: [`03-sfx-maintenance.md`](03-sfx-maintenance.md).
* **The worker PHAR** is `bin/worker.php` plus `src`, the assets, the docs, the languages and the
  `--no-dev` vendor `*.php` (`shell-package.json`'s `phar`), behind phpmicro's extra-INI block. The
  stub and its PHAR are two files and stay two: see [`02-signing-architecture.md`](02-signing-architecture.md).
* **The bundle:**

  ```
  Grafida.app/Contents/
    Info.plist                     generated by shell-packager
    MacOS/Grafida                  the shell (CFBundleExecutable)
    MacOS/grafida-worker           the phpmicro sibling-phar SFX stub
    Resources/grafida-worker.phar  the worker payload (extra-INI block + PHAR)
    Resources/shell.json
    Resources/Grafida.icns
    Resources/LICENSE.txt
  ```

  There is no `assets/` directory and no dylib: the worker serves the SPA from inside its PHAR.
* **`Info.plist` is generated.** shell-packager computes `CFBundleIdentifier` (**`app.grafida`**,
  the manifest `id`; Boson's was `app.grafida.desktop`), the names, the version (from the
  CHANGELOG, through `--app-version`), the icon and `LSMinimumSystemVersion` **12.0**. Both binaries
  must be thin Mach-O files of the bundle's architecture whose `minos` (from `LC_BUILD_VERSION`) is
  at most 12.0, or the build fails: an `Info.plist` must never offer the app to a Mac it cannot run
  on. Grafida adds only `macos.infoPlist` (the copyright, the category and
  `NSAppTransportSecurity → NSAllowsArbitraryLoadsInWebContent`); a key shell-packager computes is
  an error there.
* **Signing.** With `MACOS_SIGN_IDENTITY` set, the Developer ID, with a secure timestamp
  (`--timestamp`); without it, ad hoc. **Always with the hardened runtime** (`--options runtime`),
  so an ad-hoc build runs under the same restrictions as the notarised one. Inside-out: the worker
  stub, the shell, then the bundle. Each signature is verified (`codesign --verify --strict`) and
  read back: the hardened runtime on each binary, and exactly the configured entitlements. A stub
  with a PHAR still appended is refused, never signed.
* **Entitlements are per binary.** The shell has none. The worker has only
  `com.apple.security.cs.allow-jit`, from `build/macos/shell-worker.entitlements`
  (`macos.entitlements.worker` in `shell-package.json`): PCRE's JIT maps its code with `MAP_JIT`, and
  without the entitlement every worker start logs "Allocation of JIT memory failed" and every
  `preg_*` runs interpreted. Add an entitlement only with the test that fails without it.
* **The worker is run before the image is written:** an ini probe and the protocol's `ready`
  handshake, on the signed stub inside the finished bundle (so it also proves the stub finds
  `../Resources/grafida-worker.phar` under the hardened runtime). arm64 runs natively; x86_64 runs
  under Rosetta 2 when this Mac has it, and is otherwise skipped with a note.
* **The image** holds the bundle and an `/Applications` link, laid out by Finder from
  `macos.dmg` (background, window, icon positions; best-effort through AppleScript, which needs
  Finder's Automation permission; `--no-style` skips it), then gets its volume icon. It is UDZO,
  and signed with the Developer ID when there is one.
* **Notarisation** runs when `MACOS_NOTARY_PROFILE` is also set: `notarytool submit --wait`,
  `stapler staple`, `stapler validate`, then `spctl` on the image. A profile without an identity is
  an error (notarisation needs a Developer ID signature).
* **Reproducibility.** The script sets `SOURCE_DATE_EPOCH` to the commit time, so the PHAR inside
  is the same for one commit. The bundle and the image are not reproducible: `codesign` and
  `hdiutil` are not.

Verified with this setup on arm64: Gatekeeper reports "Notarized Developer ID" for the image and
for the app inside it (gh-88).

### Verifying a finished build

shell-packager runs the image checks itself when it notarises. By hand (`amd64` for the Intel
build):

```bash
codesign --verify --deep --strict --verbose=2 build/shell-macos/arm64/Grafida.app
codesign -d --entitlements - build/shell-macos/arm64/Grafida.app/Contents/MacOS/grafida-worker
spctl -a -vv -t open --context context:primary-signature build/dist/Grafida-<version>-macos-arm64.dmg
xcrun stapler validate build/dist/Grafida-<version>-macos-arm64.dmg
```

If notarisation is rejected, get the details with:

```bash
xcrun notarytool log <submission-id> --keychain-profile "grafida-notary"
```
